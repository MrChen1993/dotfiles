# myreview：当前 git 改动的多智能体 Java 深度 review

## 这个 skill 在做什么

对**当前 git 改动**（不是整个仓库）做一次有深度的代码审查。核心思路是**分而治之**：
与其让一个 agent 在一遍扫描里同时盯正确性、并发、性能、可读性——注意力会被摊薄，
不如**派多个只读 subagent 并行审查，每个专注一个维度**。这样每个 agent 都能在自己
的领域里挖得更深，主对话也不会被几千行 diff 和中间推理塞满。

审查完成后，本 skill 把所有发现**按严重程度归并分级**，出一份报告。

**重要边界：本 skill 只审查、出报告，自己不动手改代码。** 对于那些机械、可自动清理
的小问题（命中 code-style 规则的），它会标注为「可 auto-fix」并提示你去跑
`/auto-fix`——「动手清理」是 auto-fix skill 的职责，myreview 专注「动脑找问题」。
这样两者职责清晰：一个审查员，一个清理工。

## 前提与适用

- 输出**一律用中文**。
- 仓库用的是 **changelist 模式，git 暂存区是关闭的**。所以收集改动时**不要看暂存区
  / 不要 `git add`**，直接用「工作区 vs HEAD」加上未跟踪文件。
- 主审 **Java 代码**。非 Java 文件（配置、SQL、前端等）顺带扫一眼即可，不必动用
  全部维度。

## 整体流程

```
1. 收集改动 → 2. 并行派 4 个 review agent → 3. 汇总分级 → 4. 出报告（含「可 auto-fix」标注）
```

---

## 第 1 步：收集当前改动

先确认在 git 仓库里，再收集改动。**暂存区是关的**，所以这样取：

```bash
# 改动的文件清单（含未跟踪文件），相对 HEAD
git status --porcelain
# 已跟踪文件的 diff（工作区 vs HEAD）
git diff HEAD
```

把完整 diff 落到一个临时文件，让每个 review agent 读同一份快照、避免各自重复跑
git，也避免审查过程中文件被改动导致前后不一致：

```bash
git diff HEAD > /tmp/myreview-diff.patch
```

未跟踪的新文件不在 `git diff HEAD` 里，单独列出它们的路径，连同上面的 patch 一起
交给 review agent（让 agent 自己去读这些新文件的完整内容）。

**几个边界情况：**
- 不在 git 仓库 → 直接告诉用户，问是否要改成 review 指定文件。
- 没有任何改动 → 告诉用户「当前没有未提交的改动」，问是否要 review 最近一次提交
  （`git diff HEAD~1 HEAD`）或指定文件。
- 改动里没有 Java 文件 → 照常 review，但提醒用户本 skill 的强项是 Java。

把这一步的产物整理清楚：**改动文件清单**、**patch 路径**、**未跟踪新文件清单**。
下一步要原样传给每个 review agent。

---

## 第 2 步：并行派发 review agent（只读）

**在同一轮里**一次性派发下面这些 subagent（用 `Explore` 这类只读 agent——review
阶段绝不改代码）。并行的意义在于：它们互不阻塞、各自深入，且都不会把中间推理倒进
主上下文。

每个 agent 固定审一个维度：

| 维度 | 重点看什么 |
| --- | --- |
| **正确性 / bug** | 空指针、边界与 off-by-one、异常处理与吞异常、事务边界、资源未关闭 / 泄漏、`equals`/`hashCode`、自动装箱陷阱、`==` 比较对象、集合误用、返回 null、逻辑分支漏写 |
| **并发 / 线程安全** | 竞态、可见性（缺 `volatile`/同步）、锁粒度与死锁、线程池配置与拒绝策略、`ThreadLocal` 泄漏、共享可变状态、非线程安全集合被并发访问、`@Transactional` 与多线程 |
| **性能 / 资源** | 循环内重复查询 / N+1、循环内建对象或字符串拼接、集合初始容量与选型、不必要的全量加载、缓存缺失或失效、IO / 连接未复用、大对象驻留 |
| **可读性 / 规范 / 设计** | 命名、分层与职责、重复代码、过长方法、魔法值、注释与实际不符、Spring 用法（注入方式、Bean 作用域、循环依赖）、可复用与可维护性 |

**给每个 review agent 的指令模板**（替换 `<维度>` 和对应重点）：

```
你是一次 Java code review 的 <维度> 审查员。只审查这次 git 改动，不要改任何代码。

- 改动 patch：/tmp/myreview-diff.patch
- 未跟踪的新文件：<路径清单，让你自己读完整内容>
- 必要时可以读改动周边的代码来理解上下文，但只评审「这次改动引入或触及」的问题。

只关注 <维度> 这一个维度，重点看：<该维度的重点清单>。
不要捎带评论其它维度——其它维度有专人负责。

每条问题严格按下面的格式返回（没有问题就回「无」）：

[严重程度] 文件路径:行号 — 一句话问题描述
  · 为什么是问题：……（简明扼要，说清后果）
  · 建议改法：……
  · 可 auto-fix：是/否

严重程度三选一：
- 阻断：会导致 bug、数据错误、线上故障、安全隐患，必须改。
- 建议：不至于出错但明显该改，影响质量 / 性能 / 可维护性。
- 提示：锦上添花的小优化或风格问题。

「可 auto-fix」判定：**严格以 ~/.claude/rules/code-style.md 为准**——先读那个文件，
一条问题只有命中里面某条规则、才标「可 auto-fix：是」（意思是 /auto-fix 能自动清理
它）；没命中的一律标「否」。这只是个标注，方便用户事后决定要不要跑 /auto-fix，
myreview 自己不会去改。
```

---

## 第 3 步：汇总、归并、分级

收齐所有 review agent 的返回后，在主对话里做整合（这一步信息量不大，留在主上下文
没问题）：

1. **去重合并**：不同维度可能指向同一处（如同一行既是性能又是可读性问题）。同一
   `文件:行号` 的重复项合并成一条，保留最高的严重程度，问题描述合并表述。
2. **分级排序**：阻断 → 建议 → 提示。
3. **统计「可 auto-fix」**：数一下有多少条标了「可 auto-fix：是」，报告末尾会单独
   列出来，方便用户决定要不要跑 `/auto-fix`。

---

## 第 4 步：输出报告

用中文按下面结构汇报。先给整体判断，再给明细：

```
## Review 小结
一句话总体评价（这次改动整体质量如何、有没有必须处理的硬伤）。
共发现 N 个问题：🔴 阻断 a · 🟡 建议 b · 🔵 提示 c。

## 🔴 阻断（必须处理）
1. `文件:行号` — 问题描述
   - 为什么：……
   - 建议：……
（无则写「无」）

## 🟡 建议
（同上格式）

## 🔵 提示
（同上格式）

## 🧹 可 auto-fix（共 K 项）
列出所有标了「可 auto-fix：是」的项，每条标号。这些是机械的小问题，可以跑
`/auto-fix` 一键清理，不必在这里手工处理。
```

报告末尾，如果存在「可 auto-fix」项，加一句交棒提示：

> 其中 K 项是机械的小清理（变量名冗余、日志占位符等），直接跑 `/auto-fix` 就能自动
> 处理，不用我在这逐条改。

**始终不要在 myreview 里动手改代码。** 这是和 auto-fix 的分工底线：myreview 负责把
问题看清楚、说明白，改不改、怎么改交给 auto-fix 或你本人。

---

## 调用小抄

- 默认：review 当前 git 改动，出分级报告 + 「可 auto-fix」清单，**不改代码**。
- 指定文件（如「review 一下 OrderService.java」）：把审查范围换成该文件的整体
  review，而非只看 diff。
- 想自动清理机械问题：用 `/auto-fix`（独立 skill），不要让 myreview 代劳。

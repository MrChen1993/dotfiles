# auto-fix：按 code-style 规则自动清理当前 git 改动

## 这个 skill 在做什么

典型场景：产品定义需求 → AI 按需求开发完一轮 → 代码能跑，但留下一堆**机械的小毛病**
（变量名冗余、日志拼接、无用 import、该用封装工具却写了裸 Stream、委托字段注解不规范……）。
本 skill 就是这一轮之后的**自动收尾**：对照规则把这些毛病一次清掉，省得你手工抠。

它和 `myreview` 是一对分工明确的搭档：

- **auto-fix（本 skill）= 动手的清理工**：只处理 `~/.codex/rules/code-style.md` 里
  **已知规则**命中的机械问题，确定性地改。不找 bug、不做主观评审。
- **myreview = 动脑的审查员**：四维度深挖 bug 和质量问题，出报告，但不改代码。

所以 auto-fix 跑得轻、跑得勤（每轮开发后都可以来一遍）；要做深度体检时才上 myreview。

## 前提与适用

- 输出**一律用中文**。
- 仓库用的是 **changelist 模式，git 暂存区是关闭的**。收集改动时**不要 `git add`**，
  直接用「工作区 vs HEAD」加未跟踪文件。
- 主要处理 **Java 代码**。
- **唯一的规则来源是 `~/.codex/rules/code-style.md`**。本 skill 不自行发明规则、
  不超出该文件的范围——这是它「确定性、可预期」的根本。

## 整体流程

```
1. 收集改动 → 2. 读规则 → 3. 扫描分类（安全 / 触守卫） →
4. 安全项直接改 → 5. 汇报（已改清单 + ⚠️建议确认清单）
```

---

## 第 1 步：收集当前改动

```bash
git status --porcelain          # 改动文件清单（含未跟踪）
git diff HEAD > /tmp/auto-fix-diff.patch   # 已跟踪文件的 diff
```

未跟踪的新文件不在 diff 里，单独列出路径，后续连同 patch 一起处理。

**边界情况：**
- 不在 git 仓库 → 告诉用户，问是否改成处理指定文件。
- 没有任何改动 → 告诉用户「当前没有未提交的改动，没什么可清理的」。
- 改动里没有 Java 文件 → 告知本 skill 主要清理 Java，问是否仍要看其它文件。

## 第 2 步：读规则

完整读一遍 `~/.codex/rules/code-style.md`。这是判定「什么能改、怎么改、什么时候
要降级为建议确认」的**唯一依据**。每条规则的「命中条件 / 怎么改 / 守卫」都要吃透——
尤其是带 ⚠️ 守卫的规则（如精简字段名），守卫决定了一处到底是「安全直接改」还是
「只能建议确认」。

## 第 3 步：扫描改动，逐项分类

把这次改动里**命中规则**的地方都找出来，每一处归入两类之一：

- **安全项**：命中规则、且不触碰任何守卫——可直接改。
- **⚠️ 建议确认项**：命中规则、但触碰了守卫（会改变对外契约或数据模型），或语义上
  需要人来拍板的。**这类只记录、不改。**

判断守卫时要老老实实去查，别想当然。例如精简字段名前，要确认：字段有没有序列化 /
ORM 注解？有没有被别的文件引用？——这些都触发守卫，得归入「建议确认」。

> 工作量大、文件多时，可以按文件派只读 subagent 并行扫描分类，把结论收回来再统一
> 执行修改；改动不多时直接在主流程里做即可。

## 第 4 步：安全项直接改

**默认直接改，不逐条问。** 这是 auto-fix 作为「例行清理工」的定位——安全项本就是
「改了几乎不可能出 bug」的机械改动，且一切都落在工作区、靠 git 兜底，用户随后看
`git diff` 验收即可。

执行修改时：

- **按文件分组**：同一文件的多处修改交给同一个 fix subagent，**不同文件可并行**，
  避免两个 agent 同时编辑一个文件起冲突。
- 让 fix agent **对照 `~/.codex/rules/code-style.md` 里对应规则的「怎么改」**来改，
  保证风格统一。涉及重命名的（如精简字段名），务必**同步更新本类的 getter/setter、
  构造器、`toString` 及本类内所有引用**，不能只改声明。
- 内部数据容器 class 命中规则时，默认直接拆成独立顶级类：优先放到原内部类同 package
  下，或项目已有的 dto/vo/payload 包；保留字段、构造器、getter/setter，更新原引用，
  删除内部类。若内部类访问外部类实例状态或不是纯数据容器，降级为「建议确认」。
- 裸 enum 命中规则时，默认按 `RuntimeNodeStatus` 模板补齐 `code` / `desc`：常量改成
  `NAME("code", "描述")`，补 `@EnumValue`、`@JsonValue`、`fromCode`，并优先实现
  `CodeDescEnum`。若已有外部协议、数据库存量数据或消息体明确依赖 `name()` 的大写值，
  或 `code` 取值需要业务确认，降级为「建议确认」。
- 数据容器类 / 字段缺注释时，按规则补简洁 Javadoc：类注释说明结构代表什么，字段注释
  说明业务语义、ID 指向、时间含义、状态含义等。尤其是 `domain/repository/struct` 下被
  `@ExpandForDelegate` 复用的公共字段结构，类和所有字段都必须补齐注释。字段含义不明确
  时不要编造，降级为「建议确认」。
- `domain/service` 下真正的领域服务类命名不要重复带 `Domain`：例如
  `AemEventDomainService` 应改为 `AemEventService`，并同步更新构造器、文件名和引用。若改名
  涉及跨模块 public API、Spring Bean 名称兼容或外部反射配置，降级为「建议确认」。
- 静态建模阶段的 `domain/service` 参考 WMO / workflow：每个 `domain/entity` 实体对应一个
  `XxxService`，只继承 `BaseService<Entity, Po, Repository, StructMapper>`，不要提前写动态
  执行逻辑。若发现 service 里混入状态流转、消息处理、调度等执行逻辑，应移出当前静态建模
  变更或列为「建议确认」。
- 反复叮嘱 fix agent：**只做规则命中的那几处，绝不顺手重构或改其它东西**。改完返回
  每处的「改了什么」一句话。

**只看不改（可选）：** 用户带 `--dry-run`（或说「先看看 / 别真改」）时，跳过本步的
实际修改，只把「将会改的安全项」和「建议确认项」一起列出来给用户看。

## 第 5 步：汇报

```
## ✅ 已自动清理（共 M 处）
- `文件:行号` — 改了什么（对应规则几）
…

## ⚠️ 建议你确认（未改动，共 N 处）
这些命中了规则但触碰守卫 / 需要你拍板，没有自动改：
- `文件:行号` — 问题 + 为什么没自动改（如：字段带 @TableField，改名会动数据库列名）
  建议改法：……
…
```

末尾提醒一句：所有改动都在工作区，`git diff` 可查看验收，对某处不满意可
`git checkout -- <文件>` 撤销。

## 与 myreview 的边界

- auto-fix **只**处理 `code-style.md` 里有明确规则的机械问题。规则外的、需要判断的
  质量与 bug 问题，**不是** auto-fix 的活——那是 `myreview`。
- 如果扫描中你隐约觉得某处「可能有逻辑 bug」，但它不在规则里：**不要在 auto-fix 里
  动它**，只在汇报末尾轻描一句「这几处建议用 `/myreview` 深审一下」，交还给用户。

## 调用小抄

- 默认：清理当前 git 改动，安全项**直接改**，事后列「已改」+「建议确认」两份清单。
- `--dry-run` / 「先看看」：只列清单、不真改。
- 指定文件（如「清理一下 OrderItem.java」）：把范围换成该文件整体，而非只看 diff。
- 加规则：编辑 `~/.codex/rules/code-style.md`，即时生效（myreview 也共用这份）。
